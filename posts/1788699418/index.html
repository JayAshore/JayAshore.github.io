字节

  • 自我介绍

    简要结构：学历背景 → 技术栈（Python/Go、PyTorch、Agent、后端、MySQL、Redis、MQ）→ 重点 2 个项目（AI 智能体 + 工程落地）→ 求职方向 AI Agent 后端，擅长系统设计、可靠性与评测体系，希望做生产级智能体。

  • 挑一个有难点的项目讲一下，并讲如何解决的

    （Agent 双 Agent 项目）难点：单 Agent 幻觉高、长链路错误链式传播，缺少可靠自校验。方案：设计主执行 Agent + 校验 Judge Agent 双架构；每一步执行完成由 Judge 校验事实、规划合理性；增加轨迹快照、失败重规划；搭建自动化评测集量化幻觉率。最终降低任务失败率、幻觉指标明显优化。

  • 还有没有别的有难点的项目

    分布式 / 高并发：比如高并发数据推理服务：难点是流量波动大、资源浪费、超时不稳定；解决：消息队列削峰、负载均衡、重试幂等、容器弹性扩缩容，增加埋点可观测性。

  • 手撕：LRU

    核心：哈希表 + 双向链表 哈希 O (1) 查节点；双向链表维护最近使用顺序；get 命中移到头部；put 满了删除尾节点；线程安全版本可以加锁。

  • 场景题：1. 广告推送系统设计；2. 大流量场景分布式系统设计；

    场景题 1：广告推送系统设计
    召回：用户画像、标签库粗筛候选广告；Redis 缓存热点数据
    排序：模型打分 CTR/CVR
    过滤：去重、风控、预算、频次控制
    投放曝光埋点，MQ 异步上报日志做离线训练；分流量 A/B 测试；限流防刷。
    场景题 2：大流量分布式系统
    分层：接入层负载均衡；服务无状态水平扩容；缓存 Redis 减轻 DB 压力；MQ 削峰异步化；分库分表；限流熔断降级；全链路监控告警。

  • 消息队列实现负载均衡的方式

    消费者集群，Broker 分配分区（kafka）
    轮询、随机、一致性哈希分发消息
    消费者自动重平衡 Rebalance；空闲消费者优先分配任务

  • 消息队列实现顺序消费的方法

    保证同一业务 id 落在同一个 partition / 队列分片
    单个分区只允许一个消费者消费
    禁止多线程消费同一个分片；失败时阻塞不跳过

  • 一个队列里可能存在重复消息吗？幂等性设计

    会：Broker 宕机、消费成功 ACK 丢失，触发重试就会重复。
    幂等方案：业务唯一 ID 作为主键防重；Redis 去重；数据库唯一索引；状态机控制业务只能执行一次。

  • 消息队列怎么保证消息消费的可靠性？

    生产者：confirm 确认机制；Broker：刷盘、副本同步；消费者：手动 ACK，业务执行成功再提交 ACK；失败重试 / 死信队列。

  • 消息队列集群是怎么设计的？

    Broker 多节点，数据分片分区；副本机制保证高可用；ZooKeeper/Nacos 做元数据管理、主从选举；横向扩容分区提升吞吐；故障自动转移。

    如果我入职，最需要补强的能力是什么？

  • 为什么双 Agent，如何优化

    原因：执行模型擅长工具调用，但是自我纠错能力弱；独立 Judge 专注事实校验，解耦职责，降低幻觉。
    优化方向：Judge 模型轻量化降低成本；Bad case 回流微调 Judge；增加阶段性校验策略，不用每轮都校验减少开销；缓存校验结果。

  • MySQL锁了解吗，互斥锁怎么实现的底层原理

  • MySQL vs Redis 区别

    MySQL：磁盘持久化数据库，支持事务、复杂 SQL 查询，适合落地业务数据；
    Redis：内存 KV 缓存，高性能高吞吐，适合热点缓存、计数、分布式锁、队列；不适合大容量复杂事务存储。

  • 什么是缓存穿透、缓存击穿、缓存雪崩？

    缓存穿透：查根本不存在的数据，缓存 DB 都空，请求直达 DB
    缓存击穿：单个热点 key 过期，并发请求全部打到数据库
    缓存雪崩：大批量缓存 key 同一时间失效，数据库瞬间高并发打崩

  • 什么是限流？什么是熔断？什么是降级？

    限流：限制请求流量，防止突发大量请求压垮服务，控制单位时间允许访问的请求数量。
    熔断：依赖的下游服务故障超时 / 报错率过高时，直接切断调用，不再请求故障服务，避免雪崩。
    降级：系统压力大或下游异常时，主动舍弃非核心功能，返回兜底简化数据，保住核心业务可用。
